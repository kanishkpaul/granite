# Let Zotero Read, Let Swift Think

Build it as a **Swift 6 app for macOS 27**. An Obsidian-compatible Markdown folder is the only source of truth. A disposable SQLite index (GRDB, FTS5 and sqlite-vec) does the work. **Zotero 10 is the paper layer**, and the app reaches it through Zotero's local HTTP API, never by writing to its database. Zotero shipped three major versions in 2026, and Zotero 10 (17 August) added write access to the local API with per-app authorization. That gives a clean split. Zotero owns paper capture, metadata, PDFs, reading, annotation, sync and citation. Your app owns claims, links between papers, ideas and code decisions, synthesis and every AI feature. Swift should make up about 85–90% of the code. The one TypeScript part is a CodeMirror 6 editor hosted in a WKWebView, alongside the Safari clipper script, which has to be JavaScript anyway. Rust waits until a benchmark demands it, and Python is used only at development time. The AI layer sits behind Apple's new Foundation Models `LanguageModel` protocol, so one session can route each request to the on-device model, a local MLX model, Apple's Private Cloud Compute or Claude based on how sensitive the notes are. Retrieval is local hybrid search with reranking. AI writes only proposals with citations a script has checked. An MCP server makes the whole corpus available to Claude Code and other agents. The features that compound are the ones that act on old material without being asked: grounded Q&A with passage citations, inline related-notes suggestions, spaced repetition on prompts you chose, typed cross-links, and a ledger of what you believe. Schema builders, infinite canvases, lifelogging and uncited AI answers are where tools in this category have died. The unfair edge is not a model. It is **a graph of your own dated claims, linked to the papers and code decisions behind them**, which no product ships. Build the headless core and the MCP server first: they pay off through Claude Code in the first week, before any window exists.

## Zotero 10's writable local API makes Zotero the paper layer, not a rival

Zotero is no longer the slow-moving tool many workflows assume. It moved to **feature releases every six to ten weeks** in January 2026 ([Zotero forum](https://forums.zotero.org/discussion/129153/a-faster-release-cycle-for-zotero)). Zotero 8 shipped on 22 January, Zotero 9 on 10 April and **Zotero 10 on 17 August 2026** ([Zotero blog](https://www.zotero.org/blog/category/news/)). The reader is now strong. It handles PDFs, EPUBs and web snapshots, and Zotero 10 added a reflowable Reading Mode you can still annotate in. Read Aloud has sentence-level highlighting and an "Annotate Sentence" button, and it reached iOS on 5 October. Zotero 10 also brought nested advanced search with annotation conditions, undo/redo and batch editing ([Zotero blog](https://www.zotero.org/blog/category/news/)). An official Android app has synced libraries and annotated PDFs since mid-2025 ([Zotero blog](https://www.zotero.org/blog/zotero-for-android/)). **Zotero core has no LLM features.** None of the 2026 release posts announces any. AI arrives only through plugins such as Beaver (an agentic sidebar with sentence-level citations) and PapersGPT ([Zotero forum](https://forums.zotero.org/discussion/126573/); [PapersFlow](https://papersflow.ai/blog/papersgpt-zotero-review)). A 2026 forum thread reports that some popular plugins ship obfuscated code that doesn't match their repositories ([Zotero forum](https://forums.zotero.org/discussion/comment/507862)). Two consequences follow. Rebuilding Zotero's reader in PDFKit would be a large job for little gain. And Zotero leaves the synthesis and AI lane completely open, so your app can own it without competing with a first-party feature.

### Five integration surfaces, and only one you should build on

| Surface | What it gives you | Role in this app |
|---|---|---|
| **Local API** `localhost:23119/api/` | Web-API-v3-compatible JSON, no pagination cap, no rate limit; saved-search execution; file paths; full text. **Zotero 10+: writes** | Primary integration, for incremental pull and limited write-back |
| Web API v3 `api.zotero.org` | Full read/write and sync; keyed; 100-item pages, 50-object writes, Backoff headers | Fallback when Zotero isn't running, or for a future iOS companion |
| `zotero.sqlite` + `storage/` | Everything, raw | Emergency or bulk-import fallback only, read-only and from a copy |
| Better BibTeX JSON-RPC | Citekey search, bibliography, pandoc filter, auto-export | Optional; don't depend on it |
| translation-server (Docker, port 1969) | Zotero's site translators run headlessly: URL or DOI → Zotero JSON | Optional; the running Zotero app already does this for you |

The local API is the backbone. Turn it on in Settings → Advanced ("Allow other applications on this computer to communicate with Zotero"). Reads then need no authentication and no rate limiting. Endpoints such as `/items/<key>/file/view/url` return a PDF's path on disk, and `GET /fulltext?since=<version>` returns changed full text. Zotero 10 adds `POST`, `PUT`, `PATCH` and `DELETE` for items, collections, saved searches, tags, full text and file uploads up to 4 GB. Changes show in the Zotero UI at once and sync to zotero.org on the next sync. Authorization goes through `POST /api/local/authorize`, which pops an Allow / Always Allow / Deny dialog and returns a 32-character key. Two cautions apply: **keys are not scoped**, so one can write to any library you can edit, and every response carries a `Zotero-Server-ID` header. A mismatch returns `412`, which means your cached version numbers are invalid ([Zotero Local API docs](https://www.zotero.org/support/dev/web_api/v3/local_api)). The web API is the slow path, with pages of at most 100 items, writes of at most 50 objects and Backoff-driven throttling ([Web API basics](https://www.zotero.org/support/dev/web_api/v3/basics); [write requests](https://www.zotero.org/support/dev/web_api/v3/write_requests)). Treat the database as off limits for writes. Zotero says direct access "should be done only in a read-only manner," that writing while Zotero runs "can easily result in a corrupted database," and that the schema "can change between Zotero releases" ([Zotero support](https://www.zotero.org/support/dev/client_coding/direct_sqlite_database_access)). Zotero also holds an exclusive SQLite lock, so live readers hit "database is locked" and have to read a copy ([Zotero forum](https://forums.zotero.org/discussion/comment/351882)).

The new cadence has already broken one integration. **Zotero 8 made the citation key a native field**, copying Better BibTeX keys into it. During the transition, CSL-JSON exports lost their `id` fields, Zettlr and other tools crashed, and disambiguation suffixes (a/b) could swap when sort order changed ([Zettlr blog](https://zettlr.com/post/on-the-recent-issues-with-zotero-8-and-better-bibtex)). So **key everything in your index on the 8-character Zotero item key and the annotation key**, and treat the citekey as a readable alias that may change. The classic bridges carry the same fragility. The Obsidian Zotero Integration plugin depends on Better BibTeX, last shipped in August 2024, and has user reports of failures after the Zotero 8 switch ([GitHub](https://github.com/mgmeyers/obsidian-zotero-integration); [Obsidian forum](https://forum.obsidian.md/t/zotero-integration-and-citations/113012)). The most capable 2026 bridge is **54yyyu/zotero-mcp**: MIT-licensed, about 5,800 stars, 41 tools by default and 53 in total, covering search, annotation extraction, Zotero 10 local writes and a ChromaDB semantic index ([GitHub](https://github.com/54yyyu/zotero-mcp)). Its tool list doubles as a checklist for the app's own Zotero adapter, and you can plug it into Claude Code today, before the app exists.

### The integration contract: pull annotations by key, write back almost nothing

The app runs one incremental loop. It calls `GET /api/users/0/items?since=<lastVersion>`, persists the version number and server ID, and walks annotation items, which are children of the attachment rather than of the bibliographic item. For each paper it regenerates a **mirror note** under `Clippings/Zotero/`. The mirror holds metadata and every highlight and comment as a block whose ID is the Zotero annotation key, so your own notes can link to `[[…#^ANNKEY]]` and every re-sync is idempotent. The mirror is raw-layer material (`origin: source`), regenerated rather than edited. The note where you think about the paper lives in `References/` and stays human-owned. **Write-back is deliberately narrow:** a `synthesized` tag, or a child note that links back to the vault note, using one "Always Allow" key. Nothing more is safe to automate. No Zotero↔Obsidian tool syncs annotation edits in both directions ([Obsidian forum](https://forum.obsidian.md/t/is-it-possible-an-obsidian-zotero-integration-that-sync-annotations-between-both-systems/48016)), and creating highlights programmatically is still an open feature request ([Zotero forum](https://forums.zotero.org/discussion/132273/feature-request-expose-api-for-programmatic-pdf-annotation-creation-highlights-notes)). Accept that and give each side one job: **Zotero is the system of record for highlights, the vault for claims.** Two practical edge cases follow. In download-as-needed mode, a storage folder may hold only Zotero's hidden `.zotero-ft-cache` text file and no PDF ([Zotero forum](https://forums.zotero.org/discussion/95839/folders-in-zotero-storage-with-only-hidden-files)). That cache is also the cheapest full-text source to index first. Deep links of the form `zotero://open-pdf/...?annotation=` are widely used, but this research did not verify them against current documentation, so test them before you build the jump-to-highlight UI around them.

| Zotero owns | Your app owns |
|---|---|
| Capture of papers (Connector, translators, DOI/ISBN import) | Claims and idea notes in your words, with typed links |
| Canonical metadata, citekeys, CSL bibliographies, citation insertion into Word or Google Docs | Linking each annotation to the claims it supports or contradicts |
| PDF/EPUB storage and file sync (300 MB free; $20/yr for 2 GB, $60 for 6 GB, $120 unlimited; or WebDAV) ([zotero.org/storage](https://www.zotero.org/storage)) | Cross-paper synthesis, Q&A, contradiction finding, all with verified citations |
| Reading, highlighting and Read Aloud on Mac, iOS and Android | Enrichment beyond Zotero (concepts, citation context) and structured parsing |
| Its own search across annotations | Spaced review, the belief ledger, and links into code and project decisions |

Enrichment needs care, because every free scholarly API tightened access in 2025–26. **Crossref** introduced its first new rate limits since 2013 on 1 December 2025. A `mailto` "polite pool" allows 10 single-DOI requests per second ([Crossref](https://crossref.org/blog/announcing-changes-to-rest-api-rate-limits/)). **OpenAlex** now requires an API key, and a free key comes with a usage budget of $1/day ([OpenAlex docs](https://developers.openalex.org/api-reference/authentication)). **Semantic Scholar** keys start at 1 request per second ([Semantic Scholar](https://semanticscholar.org/product/api)). For one person's library all of this is ample, as long as you make single-record lookups by DOI and avoid list queries. For document structure, GROBID still leads on bibliographic metadata and reference extraction ([benchmark](https://cs.paperswithcode.com/paper/a-benchmark-of-pdf-information-extraction)). Docling and Marker produce better full-document Markdown, with different strengths on tables and multi-column layouts ([dev.to comparison](https://dev.to/dmaxdev/markitdown-vs-docling-vs-marker-pdf-to-markdown-for-llms-571o)). Run them as on-demand external tools, only for papers you are actively studying. They are Java and Python processes your app invokes the way it invokes `git`, not services it ships. Licensing is a non-issue for a personal app that talks to Zotero over HTTP. Zotero's staff have challenged a closed, subscription tool built on Zotero code ([Zotero forum](https://forums.zotero.org/discussion/comment/509691)), so if you ever distribute the app, don't bundle Zotero source or its AGPL translators.

Replacing Zotero makes sense only if you never cite in a word processor, never annotate on a phone and are willing to rebuild capture. For almost everyone, Zotero's translators, sync and readers are years of free work you should rent, not rewrite.

## Swift with one CodeMirror island scores 86 out of 100

The deciding fact is that Apple's on-device stack is **first-class only from Swift**. That stack includes Foundation Models, MLX Swift, Core Spotlight, App Intents, Share and Safari extensions, and PDFKit. Apple's Python SDK for Foundation Models is a beta aimed at evaluation and batch work ([PyPI](https://pypi.org/project/apple-fm-sdk/)). Every other route, from Rust, Tauri or Electron, goes through hand-written Swift shims such as swift-rs's `@_cdecl` functions ([swift-rs](https://github.com/amodm/swift-rs)). Even Raycast, which moved its UI to web technologies in 2026, kept a Swift/AppKit host for windows, hotkeys, the menu bar and process supervision ([Raycast](https://www.raycast.com/blog/a-technical-deep-dive-into-the-new-raycast)). For an Apple-only, single-user, ML-heavy app, the platform integration therefore decides the host language.

The web stack has one real lead, and it is the editor. Marcin Krzyżanowski, who spent four years building STTextView on TextKit 2, wrote in 2025 that TextKit 2 "might not be the best tool" for editing UI. He cites an estimated document height that makes the scroller jump, fragile jump-to-end workarounds and bugs that regress between releases ([Krzyżanowski](https://blog.krzyzanowskim.com/2025/08/14/textkit-2-the-promised-land/)). SwiftUI's `TextEditor` with `AttributedString` (macOS 26+) handles basic rich text but exposes no lists, tables or TextKit hooks ([WWDC25 session 280](https://developer.apple.com/wwdc25/280/)). **MarkEdit** shows the way out. It is an MIT-licensed Swift/AppKit app whose editor core is CodeMirror 6 in the system WebView. It claims 10 MB files open quickly, keeps native Writing Tools, Services and Shortcuts, and downloads at about 4 MB ([MarkEdit wiki](https://github.com/MarkEdit-app/MarkEdit/wiki/Why-MarkEdit)). Obsidian's own Live Preview is built from CodeMirror 6 decorations, so wikilink widgets, hidden syntax, embeds and callouts have abundant prior art that coding agents know well. One WKWebView costs about 50 MB at rest, far below Raycast's full web-plus-Node move, which raised its memory from **200–300 MB to 350–450 MB** ([Raycast](https://www.raycast.com/blog/a-technical-deep-dive-into-the-new-raycast)).

| Option | Score /100 (judgment) | What decides it |
|---|---|---|
| **A′ Swift 6 + CodeMirror 6 editor in WKWebView** | **86** | Native everywhere that matters, plus the best Markdown editor available; one narrow JS bridge |
| B Rust core + SwiftUI shell (UniFFI) | 80 | Best search ecosystem (Tantivy); two toolchains and an FFI layer for one developer |
| A Pure Swift (TextKit 2 / STTextView editor) | 77 | Most native; editor risk at large files |
| C Tauri 2 | 75 | Light (about 172 MB vs Electron's 409 MB in one test) ([Hopp](https://dev.to/gethopp/tauri-vs-electron-performance-bundle-size-and-the-real-trade-offs-1el4)); Apple ML behind shims |
| D Electron | 75 | Best agent loop and editor; heaviest, and the furthest from Apple frameworks |
| E Swift + Python/TS sidecar | 73 | A second runtime to ship and supervise for little gain |
| F GPUI (Rust-native UI) | 53 | Pre-1.0 with frequent breaking changes, no PDF or prose editor ([bezel-gpui](https://docs.rs/crate/bezel-gpui/latest/source/README.md)) |

The scores are researcher judgment weighted across editor quality, Apple frameworks, PDF, performance, ecosystem, MCP maturity, agent loop, LLM fluency, maintenance and iOS reuse. They are not measurements. They are sensitive in one direction: **drop the Apple-ML and extension requirements, and Tauri and Electron rise to roughly A′'s level.** The Swift choice is only as strong as your commitment to on-device models and system integration.

The honest weakness of Swift is agent productivity, and it can be managed. Matt Gallagher's one-shot test of building a macOS SwiftUI app had Claude Sonnet 4.5 score 9/10, but with outdated idioms such as `ObservableObject`. Common failures across models were missing Swift 6 knowledge and numeric-type conversions ([Cocoa with Love](https://cocoawithlove.com/blog/llms-twelve-months-later.html)). Michael Tsai's roundup says one-shot success "is still lower than with Typescript" ([mjtsai](https://mjtsai.com/blog/2025/12/31/)). On MCP, the official Swift SDK is **Tier 3**, with no minimum conformance, while TypeScript, Python and Rust are Tier 1 ([MCP SDKs](https://modelcontextprotocol.io/docs/sdk)). The mitigations are structural. Put parsing, indexing, retrieval, the Zotero adapter and the MCP server in a `KBCore` SwiftPM package that agents build and test with `swift test` and no Xcode. Keep the app target thin and generate it with XcodeGen or Tuist, so agents never hand-edit `project.pbxproj`. Pin modern idioms in `CLAUDE.md`: `@Observable`, Swift 6 strict concurrency, `async/await`. Give agents a build-and-preview loop through Xcode's own MCP bridge, which shipped in Xcode 26.3 in February 2026 ([InfoQ](https://infoq.com/news/2026/02/xcode-26-3-agentic-coding)), or through XcodeBuildMCP ([GitHub](https://github.com/czottmann/XcodeBuildMCP)). Xcode 27 adds a "SwiftUI Specialist" agent skill ([Apple WWDC26 SwiftUI guide](https://developer.apple.com/wwdc26/guides/swiftui/)). Ship the MCP server as its own small executable on the shared index, so that if the Swift SDK lags a feature you can port that one binary to TypeScript without touching the app.

The precise roles: **Swift** for the shell, vault model, file watching, Markdown/YAML parsing, index, embeddings, model routing, PDFKit, App Intents, Spotlight, extensions and the MCP helper. **TypeScript** for the bundled CodeMirror editor and the Safari extension's content script, built with Vite and tested with Vitest, with no Node runtime shipped. **Rust** only if a measured FTS5 bottleneck appears at around 100k notes. The cure then is a Tantivy indexer in a separate process, the pattern Raycast used for its Rust indexer ([Raycast](https://www.raycast.com/blog/a-technical-deep-dive-into-the-new-raycast)), or a UniFFI library as Element X does ([element-x-ios](https://github.com/element-hq/element-x-ios)). **Python** only for development-time model conversion and prompt evals. One lesson outranks the language choice. Logseq's move from Markdown files to a database left it with a frozen "OG" product and a DB beta that reviewers warn can lose data ([Kompozy](https://kompozy.io/reviews/logseq-2-0)). **Changing the source of truth costs more than changing the UI language**, so plain Markdown as truth is the one decision never to compromise.

## Markdown stays the truth while a disposable index does the work

**Target macOS 27 only.** WWDC26 announced macOS 27 "Golden Gate" as Apple-Silicon-only, with macOS 26 as the last release for Intel Macs ([TechRadar](https://techradar.com/computing/mac-os/macos-27-golden-gate-announced-at-wwdc-2026-heres-everything-you-need-to-know)). For one owner on one Apple Silicon Mac, supporting macOS 26 would mean hand-building the model adapters that macOS 27 provides for free (see the AI section). If your Mac can't run 27 yet, ship on 26 and put the 27 APIs behind `#available`.

The storage design follows from the provenance rules that make a personal corpus trustworthy. The vault folder is canonical and stays fully Obsidian-compatible: `[[wikilinks]]`, `![[embeds]]`, `^block-ids`, flat YAML properties. The app never writes `.obsidian/` and keeps its own state outside the vault, so Obsidian stays a working fallback client and the files outlive the app. The index is a single `index.sqlite` under `~/Library/Application Support/<app>/<vault-id>/`. It never syncs, never conflicts and can be deleted and rebuilt at any time. Use **GRDB 7.x**, confirmed at 7.10.0 in February 2026 with Swift 6 concurrency support ([CocoaPods](https://cocoapods.org/pods/NewGRDB.swift)). Run it as a `DatabasePool` in WAL mode, so the indexer writes while the UI and the MCP helper read, and use `ValueObservation` to feed SwiftUI. FTS5 has been on by default since GRDB 6.7 ([Swift Forums](https://forums.swift.org/t/new-release-grdb-6-7-0/63217)). Vectors need a custom SQLite build that bundles sqlite-vec. Community packages such as grdb-vector (sqlite-vec 0.1.7, SQLite 3.47.2, GRDB 7.10.0) do this, but none is official, so vet maintenance before depending on one ([grdb-vector](https://github.com/xocialize-code/grdb-vector)). Skip SwiftData and Core Data. They want to own the data the vault already owns, and one 2024 comparison found SwiftData reads "degraded sharply" above about 100,000 objects ([Emerge comparison summary](https://cal1.lr.ggtyler.dev/r/iOSProgramming/comments/1dkmdeb/swiftdata_vs_realm_performance_comparison)).

```
Vault/  (canonical, Obsidian-compatible; git repo with its .git kept outside any iCloud folder)
  AGENTS.md            rulebook for every agent, including the app's own
  Notes/               HUMAN: ideas, claims, Decisions        origin: human
  References/          one note per paper/book/tool, yours    origin: human
  Daily/  Projects/<name>/  Attachments/
  Clippings/           RAW, untrusted: Defuddle web clips      origin: source
    Zotero/<key>.md    regenerated annotation mirror, block IDs = annotation keys
  AI/                  DERIVED: index, digests, synthesis, Proposals/   origin: ai
  Private/             ai: local — never leaves the device

~/Library/Application Support/<app>/<vault-id>/index.sqlite   (disposable)
  notes · properties · tags · links (incl. unresolved) · blocks · blocks_fts · chunks_vec
  zotero_items · annotations · claims · proposals · model_calls (audit log)

App bundle
  KBCore (SwiftPM)   parse · index · retrieve · Zotero adapter · model router · verifier
  KBCapture          App Intents · hotkey panel · Share/Safari extensions → Inbox
  KBUI               SwiftUI + AppKit shell; CodeMirror 6 editor in WKWebView
  kb-mcp             stdio MCP helper reading index.sqlite read-only
```

File watching has to assume that other writers will race the app: Obsidian, git checkouts, iCloud and agents. Use the FSEvents C API on the vault root and persist the last event ID, so edits made while the app was closed replay on launch. Reconcile at startup by mtime, size and content hash. Treat atomic saves (write a temp file, then rename) as delete-plus-create pairs, and send the app's own writes through `NSFileCoordinator`, tagged with their hash so the echoed event is ignored. If the vault lives in iCloud Drive, files can be evicted to placeholders, links to evicted files break, and `NSMetadataQuery` misses some updates. That makes periodic rescans mandatory and "Keep Downloaded" advisable ([mjtsai](https://mjtsai.com/blog/wp-json/wp/v2/posts/21443); [Apple Developer Forums](https://developer.apple.com/forums/thread/664089)). History comes from git, called through `/usr/bin/git` and auto-committed on idle. The `.git` directory must live outside any iCloud folder (`--separate-git-dir`). CloudKit fits only small app state such as saved searches, never notes. FSNotes, a Swift app built on plain files with iCloud and optional git, has already proved this model works ([FSNotes](https://GitHub.com/glushchenko/fsnotes)).

The editor is CodeMirror 6 behind a narrow bridge. Text and selection go in, edits and commands come out, and Swift owns all file I/O. Spike it in the first week against a 50,000-line file and a CJK input method, and put the editor behind a protocol so a native STTextView fallback stays possible. **PDFKit** covers the rest of reading. Nutrient's own migration guide calls it "a great starting point" ([Nutrient](https://www.nutrient.io/guides/macos/migration-guides/migrating-from-apple-pdfkit/)). Use it to display a paper at a highlight, and to read and annotate PDFs that aren't in Zotero, such as manuals and specs. Its text extraction has no reading order for multi-column papers, which is why structured parsing goes to GROBID or Docling. Scanned pages go to Vision OCR, which Foundation Models now exposes as an `OCRTool` ([Apple](https://developer.apple.com/documentation/updates/foundationmodels.md)). Commercial SDKs such as Nutrient start around €5,000 ([Capterra](https://www.capterra.com/p/171174/PSPDFKit-SDK/pricing/)), which is absurd for a personal tool.

Every capture path ends in one Swift capture service that writes a Markdown file with frontmatter into an inbox. Build an **App Intent first**. On macOS 26 one intent serves Shortcuts, Spotlight actions and Quick Keys ([WWDC25 session 260](https://developer.apple.com/videos/play/wwdc2025/260?time=76)). On macOS 27, entity schemas feed your notes into Spotlight's semantic index so Siri can surface them with attribution, and an `AppIntentsTesting` framework validates the integration without UI automation ([Apple WWDC26 macOS guide](https://developer.apple.com/wwdc26/guides/macos/)). Then add a global-hotkey `NSPanel` for quick capture and a Share extension. Web clipping is a solved problem. **Defuddle**, Steph Ango's MIT-licensed successor to Mozilla Readability, turns a live DOM into clean Markdown with footnotes, math and code blocks normalized ([Defuddle](https://github.com/kepano/defuddle)). Run it in a Safari Web Extension content script, which captures logged-in and JavaScript-rendered pages, or simply keep using the Obsidian Web Clipper pointed at the same vault. Papers should never come in through your clipper. They come through the Zotero Connector, and the app picks them up on the next sync. Give every capture one cheap nudge toward processing: an optional single line saying *why* you saved it. Without that step, the inbox becomes the graveyard that the collector's-fallacy literature describes ([zettelkasten.de](https://zettelkasten.de/posts/collectors-fallacy/)).

Distribute the app to yourself with **Developer ID or local signing, no Mac App Store, no App Sandbox.** The sandbox would force security-scoped bookmarks on the vault, block shelling out to `git` and the PDF parsers, and complicate the MCP helper. Extensions are always sandboxed, so they hand captures off through an App Group container. Use plain SwiftUI with Observation, actors for the indexer and watcher, and SQL-backed paged queries, and never load 100,000 notes into memory. Skip TCA. Use AppKit where SwiftUI is still weak on the Mac: custom selection, focus and context-menu state remain gaps after WWDC26 ([Paulo Andrade](https://pfandrade.me/blog/swiftui-mac-assed-wwdc26-update/)). A ⌘K command palette that reuses the App Intent definitions keeps a single list of actions.

## One LanguageModelSession routes every request by sensitivity, not by vendor

WWDC26 changed the AI architecture more than anything else in this report. In the OS 27 releases, Apple's Foundation Models framework gained a **`LanguageModel` protocol** for using "any large language model — server or on-device". It also gained a `PrivateCloudComputeLanguageModel` and adapters for MLX and Core AI ([Apple Foundation Models updates](https://developer.apple.com/documentation/updates/foundationmodels.md)). On 8 June 2026 Anthropic released a Swift package that plugs Claude into the same framework, with streaming, tool calls and structured responses ([Claude blog](https://www.claude.com/blog/claude-for-foundation-models)). The practical effect: prompts, `@Generable` typed outputs and `Tool` definitions are written once, and a `ModelRouter` picks the backend with a single switch.

| Route | Runtime and limits | Cost | Use it for |
|---|---|---|---|
| On-device Apple model | 4K context (8K on newer devices in OS 27), about 85 tok/s, about 27 MB in-process ([WWDC Notes 319](https://wwdcnotes.com/documentation/wwdc26-319-build-with-the-new-apple-foundation-model-on-private-cloud-compute/); [apple-silicon-llm-bench](https://github.com/john-rocky/apple-silicon-llm-bench)) | Free | Tag and title suggestions, link justifications, chunk context prefixes, claim extraction from short notes |
| Local MLX model (Qwen3-4B/8B, Gemma 4 E4B, 4-bit) | Qwen3-8B about 90–98 tok/s and Gemma 4 E4B 113.5 tok/s on M4 Max, vs 80.5 on llama.cpp; several GB of memory ([apple-silicon-llm-bench](https://github.com/john-rocky/apple-silicon-llm-bench)) | Free, optional download | Anything touching `Private/`; long-context work that must stay local |
| Private Cloud Compute | 32,768 context, reasoning levels; managed entitlement, per-user daily quota, no offline use ([WWDC Notes 319](https://wwdcnotes.com/documentation/wwdc26-319-build-with-the-new-apple-foundation-model-on-private-cloud-compute/)) | Free under 2M downloads | Interactive medium-difficulty reasoning on non-private notes |
| Claude (Haiku / Sonnet / Opus 5.5) | Frontier quality; citations, caching, batches through the Messages API | $0.10/$0.50, $2/$10, $4/$20 per MTok in/out; batch 50% off ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)) | Literature synthesis, contradiction checks, nightly digests |

Routing is a code-level policy, never a prompt. Every note inherits an `ai: local | pcc | cloud | none` label from its folder, and `Private/` is `local`. Labels propagate as taint: if any chunk retrieved for a request is `local`, the whole request stays local, and a derived note built from private sources inherits the strictest label. The MCP server applies the same filter, because an MCP client such as Claude Desktop sends what it receives to the cloud. Three uncertainties belong in the design. MLX decode runs 1.5–2× faster than llama.cpp on these benchmarks, but the author warns that quantization differs between runtimes. PCC's eligibility for an app distributed outside the App Store is undocumented, so treat it as an optional tier. And the Claude Foundation Models package is a 0.1 beta whose support for prompt caching and citations is unconfirmed. Use **two transports**: the Foundation Models adapter for interactive tool flows that share code with the local path, and a thin hand-written `URLSession` client for `/v1/messages` when you need caching, citations, batches or the Files API. Store your API key in the Keychain, never in the vault. At these prices, cloud cost is trivial for one person. By the official prices, a retrieval-augmented answer over 8K tokens of context costs about **$0.02 on Sonnet 5.5 and $0.001 on Haiku 5.5**. A nightly digest of 50 changed notes through the Batch API costs about **$2 a month**. A 30-paper synthesis on Opus 5.5 runs around $0.70, and cache hits cut follow-up questions to about $0.03.

Retrieval is a Swift port of the qmd design that has become the reference for personal corpora. It runs BM25 over FTS5 and dense vectors over sqlite-vec, fuses them with reciprocal rank fusion, reranks the top 20–50 with a cross-encoder, then **expands one hop along wikilinks and backlinks**, because your links already are the knowledge graph and an LLM-extracted graph adds cost without reliable gains. The pipeline order matters more than model choice. In Anthropic's experiments, contextual chunk prefixes cut retrieval failures by 35%, adding contextual BM25 by 49%, and adding a reranker by **67%** ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). For embeddings, use **EmbeddingGemma** (308M parameters, under 200 MB quantized, 2K context, multilingual) ([Hugging Face](https://huggingface.co/blog/embeddinggemma)) through `MLXEmbedders` in mlx-swift-lm ([GitHub](https://github.com/ml-explore/mlx-swift-lm)). Qwen3-Embedding-0.6B is an alternative, but it pre-allocates a 32K-token cache that used about 5.8 GB in one test unless you cap its sequence length ([regolo.ai](https://regolo.ai/embeddinggemma-2-vs-qwen3-embedding-benchmarks.md)). Rerank with Qwen3-Reranker-0.6B. Generate contextual prefixes with the free on-device model, which fits a short bounded task in 4K. Store `embedding_model_id`, dimension and chunker version on every vector row, so an upgrade triggers a background re-embed instead of mixing vector spaces. Zotero annotations, clipped pages and your notes become blocks in the same index, which is what lets one query find a highlight, the claim it supports and the decision it shaped.

AI never writes to your notes. Every feature is **a pipeline that writes proposals**: retrieve, generate a structured output that carries chunk IDs, check each citation with a deterministic Swift verifier, then land the result in `AI/` or the proposal queue with an `origin: ai` stamp. The verifier compares quoted text against the source block after normalization and drops anything that fails. Claude's citations feature returns `cited_text` with character or page locations, which makes this mechanical. It can't be combined with structured outputs in the same request, so use two passes ([Anthropic citations docs](https://platform.claude.com/docs/en/build-with-claude/citations)). Accepting a proposal turns the touched text into `ai-accepted`, which records that you endorsed it. Every model call is logged locally with its route, model, token counts and note IDs, but not the content, so you can always see what left the machine.

Clipped pages, PDFs and tool results are untrusted input. The strongest structural defense, CaMeL, separates a planner that never sees untrusted text from a quarantined model that has no tools. It cut successful prompt injections to near zero while solving **77% of AgentDojo tasks versus 84% undefended**, and it struggles exactly when the needed actions depend on untrusted content ([CaMeL paper](https://arxiv.org/pdf/2503.18813)). In a notes app, actions often do depend on content, so apply the pattern pragmatically. Tools that touch `Clippings/` are read-only or proposal-only. Cloud-bound agent loops get no web-fetch tool when private content is in context. Rendered AI output never auto-loads remote images or links, a classic exfiltration channel. Zero-width characters and hidden text are stripped at clip time.

The corpus should face outward too. The official Swift MCP SDK implements the 2025-11-25 spec with stdio and both stateless and stateful HTTP server transports ([swift-sdk](https://github.com/modelcontextprotocol/swift-sdk)). Ship a signed stdio helper inside the app bundle that reads the index read-only. Give it a qmd-like surface: `search` (hybrid, BM25 or vector), `get_note`, `get_backlinks`, `list_recent`, `get_citations(zotero_key)`, plus write tools that only file proposals. Claude Code and Claude Desktop then work over your vault, your Zotero annotations and your claims with the same privacy filter the app uses. The Claude API's own MCP connector reaches only URL servers, not local stdio ones ([Anthropic docs](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)). Server-side Claude runs therefore need a localhost HTTP option, bound to 127.0.0.1 with a bearer token. Measure everything with a small **re-find eval**: 50–200 query-to-note pairs taken from your real searches, plus 20 you write from memory. Track Recall@5/10 and MRR (mean reciprocal rank) for each pipeline change, and track accept/edit/reject rates per AI feature. Remove any feature whose acceptance stays below about 10%.

## Features compound only when they act on old material unasked

Across the tool landscape, the dividing line is clear. Features that only **store or display** do not compound: big canvases, raw lifelogs, graph views. Features that **do something with old material without the owner remembering to ask** do compound, by scheduling it, surfacing it in context, linking it or answering from it. Only one feature has hard quantitative evidence. The open spaced-repetition benchmark compared schedulers across **19,993 collections and about 729 million reviews** ([Expertium](https://expertium.github.io/Benchmark.html)), and a forum user quoting it reports FSRS-5 beating even a trainable SM-2 in 97.4% of collections ([Anki forum](https://forums.ankiweb.net/t/fsrs-vs-sm2-in-2-seperate-profiles/52171)). The scheduler is a solved, open component. The bottleneck is choosing *what* to turn into prompts. Andy Matuschak's mnemonic essays traded **35–50% extra reading time** for detailed retention ([Matuschak](https://notes.andymatuschak.org/Mnemonic_medium)), and Quantum Country produced about 54 days of demonstrated retention per question for about 95 minutes of total review ([Matuschak & Nielsen](https://numinous.productions/ttft/)). So the app should schedule *selected* prompts, not everything.

The other compounding features have strong but anecdotal support, and the failures teach as much as the successes. DEVONthink has shipped non-generative "See Also" similarity since 1.0 ([DEVONtechnologies](https://devontechnologies.com/apps/devonthink/new)). Even so, a sponsored MacStories review of DEVONthink 4 admits the reviewer hadn't used See Also or Graph much ([MacStories](https://www.macstories.net/reviews/ai-adds-a-new-dimension-to-devonthink-4/)). The likely reason is that an inspector panel waits to be opened, so related items should appear *inline*, in the editor margin and beside a paper's highlights. Grounded Q&A over your own sources is now the expected pattern. NotebookLM built its product on passage citations, and Granola rebuilt its chat in April 2026 as an agent that searches years of notes with inline citations ([WinBuzzer](https://winbuzzer.com/2026/06/09/google-adds-gemini-35-and-antigravity-to-notebooklm-xcxwbn/); [skillscouter](https://skillscouter.com/granola-review/)). The tools that search the open world fare worse. One comparison cites unnamed studies putting Elicit's search sensitivity around 39–40%, against about 94.5% for systematic-review searching ([CASRAI](https://casrai.org/compare/elicit-vs-consensus)). Treat that as directional, but it points the same way as everything else: answers should come from your corpus, with passages attached. Typed objects are the main draw of Tana and Capacities, and their main complaint is the configuration cliff. Tana users describe a "real learning curve," and its own idea board asks to simplify supertag setup ([Product Hunt](https://www.producthunt.com/products/tana/reviews); [Tana ideas](https://ideas.tana.inc/posts/526-quick-select-the-main-tag-or-drag-and-drop-to-switch-supertag-order)). A single-owner app avoids the cliff by hard-coding its handful of types. On the losing side, Heptabase reviewers warn that a big whiteboard "can sprawl into a mess" ([dev.to](https://dev.to/pickuma/heptabase-review-visual-note-taking-for-thinking-through-problems-5daa)). Rewind's screen and audio capture was switched off on 19 December 2025 after Meta bought Limitless ([9to5Mac](https://9to5mac.com/2025/12/05/rewind-limitless-meta-acquisition/)). Logseq's database version reached beta only in July 2026, with data-loss warnings ([GitClear](https://www.gitclear.com/open_repos/logseq/logseq/release/2.0.1)).

| Trigger-driven research agent | **Compounds** if output is proposals | On a new Zotero item: find claims it supports or contradicts, queue a proposal and a review card (DEVONthink 4 smart-rule pattern ([DEVONtechnologies](https://devontechnologies.com/apps/devonthink/new))) |

| Canvas | **Gimmick as storage**, fine as a view | A temporary view over existing notes for one synthesis session |

Code and project knowledge is where a personal app can go beyond anything on the market. Research tools stop at the literature, note tools stop at notes, and developer memory tools stop at code. The research found no product that links paper → claim → idea → decision → commit. The pattern to generalize is the architecture decision record: one decision per record, kept in the repository, with a status field and an immutable body whose core value is capturing *why* ([TechTarget](https://techtarget.com/searchapparchitecture/tip/4-best-practices-for-creating-architecture-decision-records)). Index your repositories where they live, read-only, and mirror only their `docs/adr/` records, `AGENTS.md`/`CLAUDE.md` files and selected commit messages into the raw layer. Write `Decision` notes yourself, and link each one to the claims and papers that motivated it and to the commit that implemented it. This part is design inference: no source tested it. But it is the clearest gap, and it is where a corpus that spans papers and code beats any single-domain tool.

One constraint governs all of this. Anthropic's January 2026 randomized trial found engineers learning with AI help scored **17% lower on mastery** overall, while high-engagement users scored 65–86% and passive delegators 24–39% ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)). The harm came from passive delegation, not from the AI being present. So the app's default posture is Socratic: it asks for your position before arguing, and shows a question before the answer in review. "Just tell me" is a mode you choose deliberately.

## Conclusion

The 2026 releases changed what "building your own knowledge app" means. Zotero's writable local API, Apple's `LanguageModel` protocol and MCP each put a stable protocol in front of something that used to be a monolith: the reader, the models and the agents. The parts you must build yourself have shrunk to three: a rebuildable index, the provenance rules that say who may write where, and the typed claim graph that ties your reading to your decisions. Those are also the only parts that compound. Readers, models and agent harnesses will be replaced several times over the life of a vault. Your item-keyed annotation links, origin stamps and dated claims carry over to every replacement unchanged.

The main risk is building the wrong half first. A native window is the most expensive and least compounding part of the project. The headless core and the MCP helper deliver most of the edge on day one through agents you already use, and they test the hardest assumptions early: Zotero sync fidelity, retrieval quality on your own corpus, and whether you actually accept AI proposals. Build the window only after the re-find eval and your weekly accept rate show the core is worth living in. Then make every surface in it, from the margin to the review queue to the capture panel, bring back something you already wrote.
