# Own the Files, Rent the Models

You can run a compounding Obsidian vault for **$0 in sync and infrastructure**, but only if you treat live sync, version history, AI access and retrieval as separate layers with separate jobs. On a Mac with an iPhone, use iCloud Drive for live sync (the only option iOS lets run in the background) and keep a git repository *outside* iCloud for history. On a Mac with Android, use Syncthing-Fork with staggered versioning plus the same git history on the Mac. Back both up with Time Machine. For AI, the 2026 pattern that works daily is a coding agent (Claude Code or Codex) running in the vault folder. It works from a vault-root rulebook (`AGENTS.md`/`CLAUDE.md`), Steph Ango's official obsidian-skills and the official Obsidian CLI. Deny rules let it read everything but write only to an AI-owned folder or a git branch you review. You don't need a vector database at first. Anthropic's own guidance is to skip retrieval under about 200,000 tokens, and Karpathy's LLM wiki ran to about 400,000 words on index files alone. Once grep starts missing your paraphrases, add one local tool, **qmd** (SQLite hybrid search with reranking, served over MCP), and skip GraphRAG, because your wikilinks already are a knowledge graph. The research on a corpus that is really "intelligent" points to one master property: **provenance**. Whatever your vault returns you will trust without checking, so AI-generated text must never become indistinguishable from what you wrote and endorsed. The best 2026 experimental evidence says AI harms understanding through *passive delegation*, not through its presence. That evidence supports the division Licklider proposed in 1960: the machine does the clerical work of getting you into position to think, and you write the claims.

## Free sync works once you separate live sync from history

Most Obsidian sync horror stories have the same few root causes, not a bad tool. The usual ones are iCloud on Windows, evicted cloud placeholders, two sync engines on one vault, edits on two devices before a sync finished, and treating Obsidian's File Recovery as a backup. Obsidian's own help names its supported free paths and warns to "avoid syncing the same vault across multiple services" ([Obsidian Help](https://obsidian.md/help/sync-notes)). So the design rule is **one sync engine per vault folder, one git writer per repository, and history kept on the machine where most edits (and all agent edits) happen.** This refines the earlier recommendation of Obsidian Sync or Syncthing plus git. Obsidian Sync at about $4–5 a month stays the least-troubleshooting fallback ([stephanmiller.com](https://www.stephanmiller.com/sync-obsidian-iphone-ipad-free/)), but you can avoid paying for it.

### iPhone: iCloud carries the notes, git outside iCloud carries the history

iCloud is Obsidian's recommended free path between macOS and iOS. Practitioners note that on iOS **only iCloud gets to run in the background**; Syncthing wrappers and git apps can't ([HN](https://news.ycombinator.com/item?id=34066824); [Obsidian Help](https://obsidian.md/help/sync-notes)). Put the vault inside the `iCloud Drive/Obsidian/` folder. On macOS 15 and later, right-click it and choose **Keep Downloaded**, because evicted placeholders silently break search, backlinks and graph. Its failure modes are specific and known: numbered conflict copies such as "Meeting Notes 2.md" with no merge prompt, corrupted `.obsidian` JSON, and stalls that show no error. Close Obsidian everywhere, let sync finish, and diff numbered copies before deleting them, since some hold unique text ([dev.to 2026](https://dev.to/eristoddle/obsidian-icloud-sync-in-2026-including-the-windows-problem-4503)).

iCloud keeps no usable version history, so add git, but keep the `.git` database out of iCloud. iCloud syncs `.git/objects` files one by one and can produce conflicted refs such as `HEAD 2` when two machines write ([mandalivia](https://mandalivia-astro.pages.dev/obsidian/tracking-obsidian-vault-changes-with-local-only-git/)). The Obsidian Git docs warn that a synced `.git` also slows mobile startup ([Obsidian Git docs](https://publish.obsidian.md/git-doc/Getting+Started)). Run `git init --separate-git-dir ~/vault-git/Vault.git` inside the vault, which leaves only a one-line pointer file in iCloud. Then commit from the Mac alone and push to a free private GitHub, GitLab or Codeberg repo. One forum user found the Obsidian Git plugin rejected that pointer-file layout ([forum](https://forum.obsidian.md/t/obsidian-git-users-how-to-put-the-git-folder-outside-of-my-vault-to-avoid-sync-issues-with-icloud/101968)), so the robust way is a launchd job running a few lines of shell every 10–15 minutes. Keep the Git plugin disabled on the phone:

```zsh
#!/bin/zsh
# ~/bin/vault-commit.sh — run by launchd every 10–15 min (Mac only)
cd "$HOME/Library/Mobile Documents/iCloud~md~obsidian/Documents/Vault" || exit 1
git add -A
dels=$(git diff --cached --diff-filter=D --name-only | wc -l | tr -d ' ')
[ "$dels" -gt 20 ] && osascript -e "display notification \"$dels deletions staged — check iCloud/agent\" with title \"Vault\""
git commit -qm "auto $(date +%F-%H%M)" && git push -q
```

The deletion alarm is my own addition, and it matters because evicted iCloud files look like deletions to git. A sudden burst of deletions or 0-byte files in the diff is your earliest warning of a sync incident. You can restore with `git checkout`. Use a `.gitignore` that drops `.obsidian/workspace*.json`, `.obsidian/cache`, `.trash/`, `.DS_Store` and any plugin `data.json` holding API keys. Keep individual attachments under 50 MiB, because **GitHub blocks files over 100 MiB** and recommends repos stay under 1–5 GB ([GitHub Docs](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)).

### Android: Syncthing-Fork, with versioning turned on everywhere

On Android, Syncthing is the strongest free engine, with one 2026 catch: the **official Android app was archived in December 2024**. The maintained client is the community Syncthing-Fork, which shipped v2.1.7.0 on 21 October 2026 alongside Syncthing v2.1.7 ([Syncthing-Fork](https://github.com/researchxxl/syncthing-android); [archived repo](https://github.com/syncthing/syncthing-android)), and Obsidian's help now points users to it ([Obsidian Help](https://obsidian.md/help/sync-notes)). Syncthing has no cloud: devices sync directly, it writes to temp files then renames (so it never leaves partial files), and it turns conflicts into `.sync-conflict-` copies instead of silently overwriting ([Syncthing docs](https://docs.syncthing.net/users/syncing.html)). The detail most guides skip is that **Syncthing versioning only archives changes received from other devices, never local edits** ([Syncthing docs](https://docs.syncthing.net/users/versioning.html)). Turn on "staggered" versioning on every device (30-second, hourly, daily, then weekly thinning) so each device archives the others' changes. Still keep git on the Mac, because a bad edit made on the Mac (by you or an agent) is versioned nowhere else. Ignore `.git`, `.obsidian/workspace*.json` and `.trash`. If you'd rather have git history on the phone itself, GitSync (open source, Android 5+ and iOS 13+, scheduled or tile-triggered background sync, in-app conflict resolution) is the maintained mobile git client. Obsidian Git's own README points mobile users there, because its in-app mobile build is "very unstable" and can crash on clone ([GitSync](https://github.com/ViscousPot/GitSync); [obsidian-git](https://github.com/Vinzent03/obsidian-git)). Never run GitSync and Syncthing on the same folder.

### Mixed devices: LiveSync if you can tolerate complexity, otherwise Syncthing plus a wrapper

If you need both iPhone and Android, or a Windows machine, there are two free options. **Self-hosted LiveSync** is the most capable. It is actively developed (1.0.44 on 1 November 2026), offers end-to-end encryption over CouchDB, S3-compatible storage or WebRTC peer-to-peer, and fits in Cloudflare R2's free tier of 10 GB with free egress ([LiveSync](https://github.com/vrtmrz/obsidian-livesync); [R2 pricing](https://developers.cloudflare.com/r2/pricing/)). It must not run alongside iCloud or any other sync engine. Its release cadence is fast enough to ship integrity bugs: 1.0.44 fixed files being **truncated in transit through S3 storage**, and the fix doesn't repair copies that were already damaged ([LiveSync releases](https://github.com/vrtmrz/obsidian-livesync/releases)). So pin a known-good version and keep git on the Mac. The other option is Syncthing on desktop and Android with Möbius Sync on iOS (free up to 20 MB, $4.99 once beyond that) or the free SyncTrain. Both iOS wrappers sync only when iOS lets them run, at roughly 5–15 minute intervals ([stephanmiller.com](https://www.stephanmiller.com/sync-obsidian-iphone-ipad-free/); [forum](https://forum.obsidian.md/t/syncthing-mobius-sync-on-ios/69569)). Don't start new setups on **Remotely Save**. Its last release was October 2024, its auto-sync "fails silently on errors," and free-tier conflicts keep whichever file is newer or larger ([remotely-save](https://github.com/remotely-save/remotely-save)). A widely read September 2026 guide still recommends it without mentioning any of this ([stephanmiller.com](https://www.stephanmiller.com/sync-obsidian-iphone-ipad-free/)).

| Your devices | Live sync | History | Independent backup | Cash cost |
|---|---|---|---|---|
| Mac + iPhone | iCloud Drive, Keep Downloaded | git (separate git dir, Mac-only commits) → private remote | Time Machine | $0 |
| Mac + Android | Syncthing + Syncthing-Fork, staggered versioning on all devices | git on the Mac | Time Machine | $0 |
| Mac + iPhone + Android/Windows | LiveSync on R2 (E2EE, pinned version) *or* Syncthing + Möbius/SyncTrain | git on the Mac | Time Machine | $0–$4.99 |
| Any, "I just want it to work" | Obsidian Sync | Its version history + git on the Mac | Time Machine | ~$4–5/mo |

### Only git and Time Machine give you point-in-time recovery

The other layers are narrower than they look. Obsidian **File Recovery** snapshots at least five minutes apart and keeps them **seven days** by default. The snapshots live outside the vault, never sync, cover only `.md` and `.canvas`, and the docs call it "not a complete backup solution" ([Obsidian Help](https://obsidian.md/help/Plugins/File+recovery)). Raise its retention to 30 days and use it as an undo button. It is also undocumented whether it captures edits made by external processes such as agents, so don't count on it for those. Git gives repo-wide history you can browse per file from Obsidian Git 2.41's History view, which also added in-app "keep ours / keep theirs / keep both" conflict resolution ([obsidian-git releases](https://github.com/Vinzent03/obsidian-git/releases)). Time Machine covers whatever git doesn't, including a damaged `.git` folder. On privacy: a private git repo is **not end-to-end encrypted**. git-crypt fixes that on desktop but breaks mobile git clients, so it suits only the Mac-only history layer. LiveSync is the free option with built-in E2EE across every device.

## Put the agent in the folder and let it write only where you review

Three AI integration patterns existed in late 2026 (in-app plugins, agents on the folder, MCP servers). The one that compounds is the second: `cd` into the vault and run Claude Code or Codex. Kenneth Reitz runs Claude Code over 467 iCloud-synced Markdown files with a roughly 200-line `CLAUDE.md`. It specifies wikilinks, a frontmatter schema, "don't create files unless asked" and "don't restructure folders," under the principle "Claude proposes, you dispose" ([Reitz](https://kennethreitz.org/essays/2026-03-06-obsidian_vaults_and_claude_code)). Eleanor Konik, an Obsidian moderator with a vault of about 15 million words, has Claude commit to git after every change and runs metadata migrations as pull requests. When she corrects the agent, she has it **write the correction back into the skill file or `CLAUDE.md`**, so the rulebook improves instead of going stale ([Konik](https://www.eleanorkonik.com/p/claude-obsidian-got-a-level-up)). Two pieces of official tooling make this pattern native. Ango's MIT-licensed **obsidian-skills** (about 50,600 stars) teaches any Agent-Skills-compatible agent Obsidian Markdown, Bases, JSON Canvas, the CLI and defuddle web extraction ([GitHub](https://github.com/kepano/obsidian-skills)). The **official CLI** has been generally available since 1.12.4 in February 2026, and its docs claim "anything you can do in Obsidian you can do from the command line". That covers search, daily-note append, property setting, `orphans`, `unresolved`, `backlinks`, `base:query` and file-history restore, with JSON output. One constraint shapes automation: **the Obsidian app must be running** for the CLI to work ([Obsidian CLI](https://obsidian.md/help/cli)).

### What to have the agent do, ranked by value per unit of risk

The recipes that pay off are read-heavy. Three practitioners arrived independently at an **agent-maintained index file**: Konik's overnight index of forgotten notes, the Hack-Log "INDEX.md" read at every session start, and Karpathy's `index.md`. It is the cheapest, most auditable "ask my vault" layer you can build ([Konik](https://www.eleanorkonik.com/p/claude-obsidian-got-a-level-up); [Hack-Log](https://note.com/hacklog_stealth/n/n8e1786d1458e?hl=en)). Reitz's best use is cross-temporal pattern questions over his own journals, such as themes in March daily notes that disappear by June. He runs a structured query first and then asks Claude to interpret the results ([Reitz](https://kennethreitz.org/essays/2026-03-06-obsidian_vaults_and_claude_code)). Hack-Log adds a useful counterweight to the "keep AI out" camp. In their vault, **54% of agent-facing notes were updated within 30 days, against zero of 134 human-facing notes**, and they conclude that "the deciding factor is whether a note is on a path that gets read regularly" ([Hack-Log](https://note.com/hacklog_stealth/n/n8e1786d1458e?hl=en)). The two positions fit together. Put AI-maintained scaffolding (indexes, maps, digests) on the read path, and keep the human-written notes clearly identifiable.

| Make the vault more valuable | Make it worse |
|---|---|
| Agent-maintained `index.md` and topic maps in an AI folder | Agents writing evergreen notes "in your voice" |
| Health reports: orphans, unresolved links, missing properties (CLI `orphans`/`unresolved`) | Bulk auto-tagging and auto-linking without review |
| Cross-temporal questions over your journals | Long AI summaries of clippings saved as if they were notes |
| Cited synthesis written to a separate folder | Unreviewed AI flashcard decks |
| Inbox triage that *proposes* filing; metadata migrations as PRs | Write-enabled agents reading un-quarantined web clippings |
| Thinking-partner mode that asks questions (Claudesidian's `/thinking-partner`) | "Always allow" on write tools |

Flashcards follow the same split. Self-made cards beat premade ones in Pan et al. (2022), at about d ≈ 0.45 for memory as reported secondhand ([Keiffenheim](https://evakeiffenheim.substack.com/p/when-ai-flashcards-pollute-your-anki-deck-and-the-4-step-workflow-that-makes-them-useful-instead)), although an earlier study found no advantage ([Learning and the Brain](https://www.learningandthebrain.com/blog/should-students-make-their-own-flashcards-take-ii/)). No head-to-head trial of AI-generated versus self-made cards had reported results by November 2026. So use AI for ephemeral "quiz me on this note" retrieval prompts, and if it drafts cards, delete most of them.

### Guardrails have to be enforced, not requested

**"CLAUDE.md instructions are not a security control"** ([aident.ai](https://aident.ai/blog/claude-code-obsidian-without-losing-notes)). Enforcement lives in `.claude/settings.json` deny rules, which are evaluated before allow rules. Deny edits to source folders and deny `rm`/`mv`. Start sessions in plan mode, and after each run check `git diff --name-status` for unexpected deletions or renames. For bulk or scheduled work, use a branch or a git worktree *outside* the synced folder, so iCloud or Syncthing never pushes half-finished agent edits to your phone. Konik also found that big agent edits strain sync and leave Obsidian's cache stale ([Konik](https://www.eleanorkonik.com/p/claude-obsidian-got-a-level-up); [evomap](https://evomap.ai/blog/obsidian-claude-code-vault-to-code-workflow)). The threat that is specific to vaults is **prompt injection through clippings**. A vault with private notes, web clippings and an agent that can write or reach the network meets all three conditions of Simon Willison's "lethal trifecta" ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Zander's remote-MCP setup shows serious mitigation. Clippings are read-only, and searches there return only paths, so reading one is an explicit, visible call. `CLAUDE.md` can't be written by tools. Zero-width and bidirectional Unicode characters are stripped. Dataview JS and Templater stay off, because agent-written notes could otherwise become executable code. He concedes these guards can't catch a visible instruction, so the last line of defense is a per-write approval prompt ([zander.wtf](https://zander.wtf/blog/obsidian-mcp-pi/)).

### MCP, mobile access and local models

There is **still no first-party Obsidian MCP server**. The Local REST API plugin has served MCP at `/mcp/` since v4.0 (May 2026), which makes the older mcp-obsidian wrapper legacy. cyanheads/obsidian-mcp-server (v3.7.0, October 2026) is the deepest REST-backed option, with section-aware patching and command dispatch off by default ([ContextBolt](https://contextbolt.com/blog/obsidian-mcp-claude/), a vendor-written comparison). If your agent has shell access, you mostly don't need MCP at all: files plus the CLI do more. MCP earns its place for **"ask my vault" from the phone**. Zander runs a roughly 100-line FastMCP server on an always-on Raspberry Pi behind GitHub OAuth and Tailscale Funnel. He adds it once as a Claude custom connector, and it then works in the Mac app, on the web, on the phone and in Claude Code ([zander.wtf](https://zander.wtf/blog/obsidian-mcp-pi/)). A free version of the same idea is a home Mac mini serving the iCloud or Syncthing copy of the vault, read-only by default. That is my extrapolation, not something a source tested. For bounded study of a single topic, NotebookLM works as a read-only "study room": export one folder with the Context Pack plugin, and don't paste its output back into permanent notes ([Context Pack](https://community.obsidian.md/plugins/context-pack-for-notebooklm)). Local models via Ollama or LM Studio handle per-note transforms (summarize a clip, extract properties) and anything sensitive. Mid-size Qwen3-family models are the common recommendation ([Layer3Labs](https://www.layer3labs.io/guides/best-local-llms)). Every published whole-vault agent workflow found still uses a frontier cloud model. If you point Web Clipper's Interpreter at Ollama, start Ollama with the browser-extension origins allowed and raise its context window, because the 2,048-token default silently truncates long pages ([Obsidian Help](https://help.obsidian.md/web-clipper/interpreter)).

## Skip the vector database until grep starts missing your paraphrases

Most people overbuild retrieval infrastructure. Anthropic's guidance is direct: **if a knowledge base is under 200,000 tokens, put all of it in the prompt with caching and skip RAG** ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). Karpathy's LLM wiki reached about 100 articles and 400,000 words navigated only through an LLM-maintained `index.md`, with no embeddings or chunking ([gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f); [Starmorph](https://blog.starmorph.com/blog/karpathy-llm-wiki-knowledge-base-guide)). Boris Cherny says Claude Code moved off a local vector database because agentic search "generally works better", though he admits the evidence was "mostly vibes" plus internal benchmarks ([OfficeChai](https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/)). In the other direction, Chroma found that **all 18 frontier models it tested degraded as input grew**, well below their maximum windows ([W&B summary](https://wandb.ai/byyoung3/ml-news/reports/Chroma-Research-Warns-of-Context-Rot-as-LLMs-Falter-with-Long-Inputs--VmlldzoxMzczMjQ4MQ)). Dumping a large vault into a 1M-token window is therefore not free even when it fits. Personal notes also differ from code in a way that matters. Code has exact identifiers. Notes written over years are paraphrastic, so grep for "burnout" misses the entry that says "exhausted, need a break." That is where hybrid semantic search earns its place.

| Vault size (your own estimate) | What to run | Why |
|---|---|---|
| Under ~150k words (a few hundred notes) | Nothing extra: agent with grep, or the whole folder in context | Under Anthropic's 200k-token line |
| ~150k–500k words with decent structure | Agent grep + an agent-maintained `index.md` | Karpathy-scale; add search only if recall frustrates you |
| Over ~500k words, thousands of notes, or many PDFs | Add **qmd** as a search tool the agent calls *alongside* grep | Paraphrase recall and context rot start to bite |

These thresholds are my synthesis. No benchmark has compared these approaches on personal note corpora.

### When you do add search, add qmd and keep the index disposable

**qmd** (tobi/qmd, MIT, about 30,800 stars) is the clearest 2026 default for an agent-centred vault. The entire index is one SQLite file in `~/.cache/qmd`, using FTS5 for BM25 and sqlite-vec for vectors, so it sits outside the vault and away from any sync engine. It splits notes into roughly 900-token chunks that prefer Markdown headings and never break code blocks. A fine-tuned 1.7B model expands each query into keyword, vector and hypothetical-answer variants. BM25 and vector results are fused with reciprocal rank fusion (k = 60) and reranked by qwen3-reranker-0.6b. Everything runs locally as GGUF models (embeddinggemma-300M by default). It serves MCP tools `query`, `get`, `multi_get`, `status` and `metadata`, and `qmd mcp --http` keeps the models warm ([qmd](https://github.com/tobi/qmd)). Karpathy's gist lists it as the optional tool to add once a wiki outgrows its index ([gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). It has no documented file watcher. Run `qmd update && qmd embed` from a launchd `WatchPaths` job, nightly, or at the start of each agent session; it is incremental, so unchanged files are skipped.

That pipeline reflects the best evidence on what matters. In Anthropic's Contextual Retrieval experiments, prepending context to chunks cut retrieval failures by **35%**, adding contextual BM25 raised that to **49%**, and adding a reranker raised it to **67%** ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). Hybrid search and reranking matter more than which embedding model you pick. Most vault notes are shorter than one chunk anyway. For longer notes, prefixing each chunk with `title > heading path` plus key frontmatter is a free approximation of contextual retrieval (my inference). Save LLM-generated chunk context for long PDFs, where Anthropic priced it at about $1.02 per million document tokens. On embeddings, privacy should decide, not cost. Hosted embeddings such as OpenAI text-embedding-3-small or voyage-4-lite cost about $0.02 per million tokens ([embeddingcost.com](https://embeddingcost.com/compare)), so a 50,000-note vault costs about a dollar to embed. The local options are good too: EmbeddingGemma scores 69.7 and Qwen3-Embedding-0.6B 70.5 on English MTEB v2, with Qwen3-Embedding-8B around 75 if you need multilingual coverage ([presenc.ai](https://presenc.ai/research/best-open-weight-embedding-models-2026)). Record the embedding model in the index metadata, so a model change triggers a full rebuild instead of mixing incompatible vector spaces.

At personal scale every embedded store is fast enough. Brute-force search over a few hundred thousand vectors takes milliseconds on Apple Silicon. That makes the choice about operations and portability: sqlite-vec plus FTS5 or LanceDB if you build your own, and Qdrant or pgvector only if they are already running ([Actian](https://www.actian.com/blog/developer/comparing-embedded-vector-databases/)). In-app plugins keep private indexes that external agents can't reuse. Smart Connections v4 keeps its index in `.smart-env/` in the vault, and its README says to exclude that folder from third-party sync ([Smart Connections](https://github.com/brianpetro/obsidian-smart-connections)). Copilot now treats semantic indexing as optional ([Copilot listing](https://community.obsidian.md/plugins/copilot)). Keep Smart Connections for its "related notes while writing" view, which is a discovery tool and not infrastructure. Khoj shows the vendor risk on the other side: its hosted cloud **shut down on 15 April 2026**, leaving self-hosting as the only option ([PromptQuorum](https://www.promptquorum.com/power-local-llm/khoj-ai-second-brain-review)).

### Your wikilinks already are the knowledge graph

LLM-extracted knowledge graphs help mainly with global "what are the themes across everything" questions, and their gains shrink under independent testing. An unbiased re-evaluation cut LightRAG's reported win rate over naive RAG on one dataset from **66.7% to 39.1%** ([arXiv 2506.06331](https://arxiv.org/pdf/2506.06331)). The 2026 WildGraphBench found no graph method winning across subsets ([arXiv 2602.02053](https://arxiv.org/pdf/2602.02053)). Building one over a vault takes hours of LLM calls, plus re-extraction every time notes change, and it produces a second graph that competes with the links you made. A better design for a personal vault is to run hybrid search, expand the hits one hop along wikilinks, backlinks and shared properties, then rerank. Your hand-made links serve as free, curated graph edges. Consider LazyGraphRAG, which Microsoft says indexes at about 0.1% of full GraphRAG's cost ([Microsoft Research](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)), only for a large PDF research subcorpus. Temporal graph memories such as Graphiti/Zep and Cognee are built for agent conversation memory, not for indexing a corpus you write yourself.

## Treat the vault as a substrate and upgrade what each primitive exposes

From first principles, a vault exposes five primitives. Every upgrade worth making builds on one of them. **Files** give agents read/write access, plus git, CI and static publishing. **Links** give a curated graph that can stand in for embeddings and can be linted for orphans. **Frontmatter** gives a typed property layer that Bases, scheduled jobs and agent state can query. **Paths** give permission scopes and provenance partitions such as `raw/` versus `wiki/`. **The running app** (CLI and URI) gives access to things that exist only at runtime: the resolved link graph, Bases query results, plugin commands, and Sync or Publish ([Obsidian CLI](https://obsidian.md/help/cli)). The 2026 change is that the CLI and Agent Skills made "vault as agent substrate" an officially supported use rather than a hack. The 1.15 early-access build also added CLI and URI commands that append under a specific heading ([1.15.0 changelog](https://obsidian.md/changelog/2026-10-22-desktop-v1.15.0/)). There is one design tension. The file layer needs no app and will outlast all of this, while the CLI layer is richer but needs a desktop session. File-only jobs, such as `claude -p` against the folder, therefore run headless. CLI jobs need a Mac that stays logged in.

| Upgrade | Primitive | Maturity, Nov 2026 | Lock-in | Verdict |
|---|---|---|---|---|
| Coding agent in the vault + `AGENTS.md` + obsidian-skills | Files, App | Daily driver | Low | Do first |
| Raw → derived split (LLM wiki) for one reference domain | Paths | Daily driver under ~100–200 sources | Low | Do, scoped |
| Automated ingestion (Web Clipper, Readwise, Granola, Screenpipe) into `Clippings/` | Files | Mature for reading and meetings; hardware fragile | Low–medium | Do, open formats first |
| Bases + CLI `base:query` as the structured layer; computed results frozen into Markdown | Frontmatter, App | Daily driver | Low | Do |
| Scheduled lint and digest jobs on a branch | Files, Links | DIY glue | Low | Month two |
| Publishing loop (Quartz/Publish) | Files | Mature | Low | When you have output |
| Human + agent multiplayer over CRDTs (Relay) | Files | Early | Medium (closed auth) | Wait |
| Personal LoRA / "digital twin" from the vault | Files | Speculative | High | Don't yet |

### The LLM wiki is right for reference knowledge, wrong for your own thinking

Karpathy's April 2026 gist has three layers: immutable `raw/` sources, an LLM-written `wiki/`, and a schema file. It defines three operations: *ingest* (one source may touch 10–15 pages), *query* (answers cite wikilinks and good ones are filed back) and *lint* (contradictions, stale claims, orphans), plus `index.md` and an append-only `log.md`. Its premise is that maintenance is why human wikis fail, so the LLM takes it over ([gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). Practitioners report a sweet spot of roughly 100–200 sources and degradation at 200,000–300,000 tokens of wiki even with 1M-token windows. Critics name two costs: you lose the learning that comes from filing material yourself, and repeated LLM rewriting compounds errors ([Starmorph](https://blog.starmorph.com/blog/karpathy-llm-wiki-knowledge-base-guide)). The resolution is in Karpathy's own directory split. Provenance separation is already built into his design. A personal corpus needs one more class he doesn't have: a **protected human layer** the LLM may read, cite and propose changes to, but never silently rewrite. Use the wiki pattern under `AI/Wiki/<domain>/` for a field you need to query, such as a market, a codebase's dependencies or a literature, with `Clippings/` as its raw layer. Keep it away from your evergreen notes. Readwise's experimental Wikiwise Mac app, which points an agent at a Markdown folder to write summary and cross-reference pages, shows that vendors are now productizing this exact pattern ([Readwise](https://wiseup.readwise.io/wiseup-vol-63-introducing-wikiwise-single-re-export-to-obsidian-and-email-filtering-in-reader/)).

### Ingestion and computation are mature; hardware and multiplayer are not

Ingestion fails in order of how closed the pipeline is. Open file formats such as Web Clipper and defuddle are the most robust. Official APIs such as Readwise and Granola come next, though Granola's API reportedly needs a paid plan ([Granola Sync](https://community.obsidian.md/plugins/granola-sync)). Reverse-engineered caches are weaker still, and single-vendor hardware is weakest: **Meta bought Limitless on 5 December 2025 and ended Pendant sales** ([CNBC](https://www.cnbc.com/2025/12/05/meta-limitless-ai-wearable.html)). Screenpipe points to where things are converging. Its scheduled agents ("pipes") are defined in a single Markdown file holding a prompt and a cron schedule, and the stock journal pipe writes a dated Markdown file into an Obsidian vault every two hours ([Screenpipe](https://docs.screenpi.pe/pipes)). That makes the automation itself a note. On computation, the DuckDB/MotherDuck plugin runs SQL inside notes and **freezes the results as Markdown tables**, with refresh cadence set in frontmatter, so agents read cached answers as plain text ([MotherDuck](https://motherduck.com/blog/obsidian-vault-duckdb-ai-agents/)). Freezing computation to text applies well beyond DuckDB: anything an agent computes should land as diffable Markdown. Multiplayer exists through Yjs plugins such as Relay ([Relay](https://github.com/No-Instructions/Relay)), but one plugin author warns that Obsidian Sync "is not" CRDT-aware and the two "don't coordinate" ([obsidian-collab](https://github.com/chikn8/obsidian-collab)). Don't layer it onto a sync setup you depend on.

### Frontier thinking: trails, belief diffs and malleability

Three frontier ideas look sound and are buildable now. The first is Vannevar Bush's **associative trails** (1945): named, ordered, annotated paths through material that can be shared ([The Atlantic](https://www.theatlantic.com/magazine/archive/1945/07/as-we-may-think/303881/)). They are still underbuilt, because PKM tools have links but not trails. An agent can now cheaply *propose* a trail through your notes, and you name it and endorse it. The second is the **belief diff**. Git history plus `supersedes` links plus dated decision records already contain everything needed for a quarterly report of the form "in March you believed X, in October you wrote Y, and source Z triggered it." No product does this yet, but a scheduled agent can. The third comes from Ink & Switch's 2025 essay on malleable software, which argues that AI code generation alone doesn't give users agency and that environments must provide the platform capabilities ([Willison summary](https://simonwillison.net/2025/Jun/11/malleable-software)). Obsidian is close to that environment already. With the CLI's developer commands, an agent can write, reload and test a plugin for your one-off need. Fine-tuning remains speculative. Practitioners agree that LoRA captures voice and style but not facts ([Centron](https://www.centron.de/en/tutorial/lora-fine-tuning-for-llms-with-custom-data/)). One person who trained on 75,000 of their own messages found the unsanitized model reproduced friends' names, addresses and card digits ([dev.to](https://dev.to/niclydon/i-trained-an-llm-on-75k-of-my-own-messages-so-it-would-stop-writing-like-a-chatbot-1dpi)). If you ever do it, train only on the human layer. A twin trained on an LLM-compiled vault mostly learns the LLM's prose, not yours.

## A personal corpus earns trust through provenance, time and your own authorship

Start from the jobs, not the tools. Re-finding is the best-measured personal information behavior: up to **40% of web queries in a year-long log were re-finding queries**, and changes to results people had seen before hampered re-finding ([Teevan et al. 2007](https://people.csail.mit.edu/teevan/work/publications/papers/sigir07.pdf)). In their own collections, people prefer navigating their own structure and treat search as a last resort, even when search improves ([Bergman et al. 2008](https://dl.acm.org/doi/10.1145/1402256.1402259)). Learning has the strongest science behind it: retrieval practice beats restudy on delayed retention ([Roediger & Karpicke 2006](https://doi.org/10.1111/j.1467-9280.2006.01693.x)). Quantum Country's essay with embedded spaced prompts produced about **54 days of demonstrated retention per question for about 95 minutes of total review** ([Matuschak & Nielsen](https://numinous.productions/ttft/)). Self-knowledge is the job most underserved and most unique to a personal corpus, because hindsight bias makes people misremember their earlier beliefs as closer to how things turned out ([Fischhoff 1975](https://doi.org/10.1037/0096-1523.1.3.288)). Only a timestamped external record can show you how your thinking actually changed.

| Job | AI's proper role | How you'd know it works (proposed metric) |
|---|---|---|
| Recall: find what I know | Hybrid retrieval with span citations and explicit "I have no note on that" | Time-to-refind; correct abstentions |
| Output and decisions | Assemble sources and propose an outline *after* you state your thesis | Time-to-draft plus whether you can defend it without the tool |
| Synthesis across time | Surface tensions between your own notes; propose trails | Share of proposed connections you accept and reuse |
| Resurfacing | Bring back old notes that need a decision | Acceptance rate under a fatigue budget |
| Reasoning partner | Socratic by default: asks for your position first | Revisions and counter-arguments you produce |
| Self-knowledge | Belief diffs from git and supersession links | Can you answer "what did I think in March, and why did it change?" |
| Learning | Generate retrieval prompts from *your* notes; withhold answers | Delayed recall |

These jobs conflict, which is why one undifferentiated "assistant" is the wrong design. The evidence from 2025–2026 is cautionary and consistent in direction, though still preliminary. In MIT's "Your Brain on ChatGPT" study (54 participants, EEG, a preprint), LLM-assisted writers showed the weakest neural connectivity, reported lower ownership of their essays and **struggled to quote their own essays** ([Kosmyna et al.](https://arxiv.org/abs/2506.08872)). A Microsoft/CMU survey of 319 knowledge workers found that higher confidence in generative AI went with less critical thinking ([Lee et al., CHI 2025](https://www.microsoft.com/en-us/research/?p=1135061)). The most decision-relevant result is Anthropic's January 2026 randomized trial. Engineers learning a new library with AI help scored **17% lower on mastery (d ≈ 0.74) with no significant speedup**, but *how* they used it mattered most: high-engagement users scored 65–86% and passive delegators 24–39% ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)). The harm comes from the delegation pattern, not from the AI being present. So the engaged pattern should be the default (state your view, then let the model argue), and "just give me the answer" should be a mode you choose deliberately.

### Provenance is the master property

Three properties are non-negotiable, and provenance underlies the other two. Clark and Chalmers' extended-mind criteria say a notebook counts as part of your cognition when it is reliably available and **automatically endorsed on retrieval**, having been consciously endorsed in the past ([Clark & Chalmers 1998](https://doi.org/10.1093/analys/58.1.7)). A vault that mixes unmarked AI text into your notes breaks the second condition. Model output becomes part of your mind without ever having been endorsed. Offloading itself isn't the problem. The "Google effect" replicated only when participants had learned the store was reliable ([Memory 2021](https://informahealthcare.com/doi/full/10.1080/09658211.2021.1962356)), and saving one file can *improve* learning of the next material ([Storm & Stone 2015](https://doi.org/10.1177/0956797614559285)). The right model is Wegner's **transactive memory**, in which partners each know *who knows what* ([Wegner 1987](https://doi.org/10.1007/978-1-4612-4634-3_9)). The goal is to know roughly what your corpus holds and where, and to trust it because its origins are legible. "Second brain" is the wrong model. The second property is **temporality**: bi-temporal systems such as Zep record when a fact held separately from when it was recorded, and invalidate old facts instead of deleting them ([Rasmussen et al.](https://arxiv.org/abs/2501.13956)). For a person, that means you *supersede* a belief with a new dated note and a link, and never overwrite it. The third is **verifiability**. LLM answers often lack full citation support ([ALCE](https://arxiv.org/abs/2305.14627)), so every AI claim should resolve to a block reference or a verbatim quote that a script can check. Ted Nelson's transclusion, which is inclusion by reference with a live link back to the origin, is the old name for provenance-preserving quotation.

The main failure mode follows from all this. It is **provenance collapse**: AI synthesis gets re-ingested as evidence, summaries of summaries flatten nuance, and over the years the corpus starts citing itself. This is a personal-scale version of the model collapse documented when models train on their own output ([Shumailov et al., Nature 2024](https://doi.org/10.1038/s41586-024-07566-y)). The mitigations are structural. Retrieval for *evidence* draws only from sources and human notes. The AI layer is derived and can be deleted and rebuilt at any time. AI links are suggestions until accepted. Agents never rename or move the files you navigate by, because changed locations break re-finding. Several problems remain open. There is no accepted metric for augmentation versus substitution. If an agent proposes hundreds of links a week, review degrades into rubber-stamping and provenance collapses anyway. No consumer PKM tool has injection-safe ingestion. And nobody has a good policy for when a past note should interrupt you. Licklider's 1960 division of labor still fits: the machine does the routinizable work of "getting into a position to think," and the human sets goals and judges ([Licklider](https://groups.csail.mit.edu/medg/people/psz/Licklider.html)).

## The reference architecture is four layers, one rulebook and five build stages

This architecture keeps the earlier type-based vault structure and adds the provenance partition the new research requires. There is one deliberate change: your own writing moves from the vault root into `Notes/`. Ango's root-level notes still work for a human, but path-based deny rules need a folder to target, and agents read paths, not tags.

```
Vault/                      # iCloud Drive/Obsidian/Vault (iPhone) or a Syncthing folder (Android)
  AGENTS.md                 # model-agnostic rulebook; CLAUDE.md contains one line: @AGENTS.md
  .claude/                  # skills/ (kepano obsidian-skills) + settings.json (deny rules)
  Notes/                    # HUMAN layer: evergreen notes, essays, decisions, timestamped captures
  Daily/                    # YYYY-MM-DD; capture target for CLI/URI daily:append
  References/               # one note per book/person/paper/tool (human-owned; agent may draft into AI/)
  Clippings/                # RAW layer: Web Clipper, Readwise, transcripts — agents read, never edit
  AI/                       # DERIVED layer: regenerable, deletable
    index.md  log.md        # agent-maintained catalog; append-only operations log
    Wiki/<domain>/          # LLM-wiki pages for scoped reference domains
    Digests/  Review/       # weekly digests, health reports, retrieval prompts
    Proposals/              # suggested edits/links/merges to human notes, awaiting accept/reject
  Private/                  # sensitive; denied to cloud agents, local models only
  Projects/  Archive/  Attachments/  Templates/
```

The frontmatter schema from the earlier report gains one mandatory field and two optional ones. `origin: human | source | ai | ai-accepted` gets stamped by templates and agents. Use it instead of the earlier `author: ai` suggestion, which collided with `author` as a book-author field. `supersedes: ["[[old note]]"]` and `as_of: 2026-11-03` apply to claims that can go stale. Add `^block` IDs only to claims that something cites. Files under `Notes/` default to `origin: human`. When you accept and rewrite something from `AI/Proposals/`, it becomes `ai-accepted`, which records the endorsement. The rulebook and permissions together are short:

```jsonc
// .claude/settings.json — test each rule on a disposable file first
{ "permissions": { "deny": [
  "Edit(./Notes/**)", "Write(./Notes/**)", "Edit(./Clippings/**)",
  "Read(./Private/**)", "Edit(./AGENTS.md)", "Bash(rm *)", "Bash(mv *)" ] } }
```

`AGENTS.md` should state what each folder means, the `origin` rule ("you write only to `AI/`; changes to human notes go to `AI/Proposals/` as diffs"), the citation rule (every claim links a note, block or quote), "never rename or move files," and "commit with author `agent` after each task." Following Konik, add one more rule: when you correct the agent, it drafts an `AGENTS.md` amendment into `Proposals/` for you to apply. That keeps the rulebook improving without letting a session that just read a clipping rewrite its own rules.

| Stage | When | Build | Done when |
|---|---|---|---|
| 1. Safety net | Day 1 | Your device branch's sync; separate-git-dir repo; launchd commit script with deletion alarm; private remote; Time Machine; File Recovery at 30 days | You've restored one note from git and one from Time Machine |
| 2. Rulebook | Week 1 | Folders above; `origin` in templates; `AGENTS.md`; obsidian-skills in `.claude/`; deny rules; Smart Connections for related notes | An agent session in plan mode produces only new files in `AI/` |
| 3. Read-path agents | Weeks 2–4 | `AI/index.md` maintenance, weekly health report (CLI `orphans`/`unresolved`), Socratic weekly review over `Daily/`, inbox triage into `Proposals/` | You open the index or digest weekly, and accept or reject proposals |
| 4. Retrieval | When grep misses (≈500k words) | qmd over `Notes/`, `References/`, `Clippings/`, `AI/`; MCP for Claude Code and Desktop; refresh at session start or via launchd | Paraphrased queries find the right note in the top five |
| 5. Compounding loops | Quarter 1–2 | Nightly lint on an `agent/` branch; one scoped LLM wiki; quarterly belief diff; a low-bar publishing stream; optional phone MCP connector from an always-on Mac | Your own writing is cited in finished output each month |

Cash cost for stages 1–4 is zero; Möbius at $4.99 is optional on mixed-phone setups. The one recurring cost is the model you rent. Local models are the free fallback for sensitive material and per-note transforms, but nothing found shows them handling whole-vault agentic work well yet.

## Conclusion

The research changes the order of priorities. A year ago the main decision in building a knowledge base was the tool stack: which sync, which plugin, which vector database. By November 2026 those decisions are cheap and reversible, because everything durable is Markdown and YAML, and every index can be rebuilt from it. The decisions that don't reverse cheaply are about *governance*. Who can write where, how origin is recorded, and whether a belief is superseded or overwritten all compound for good or ill over years. Sync and AI also turn out to be coupled. Your sync engine distributes an agent's mistakes, and your history layer is the agent's undo button. That is why git becomes mandatory the day an agent gets write access, and why agent work belongs on a branch outside the synced folder.

The deeper point is that an "intelligent" personal corpus is defined less by how much it can answer than by **how much of what it returns you can trust without checking**. The design goal is to keep that trusted set accurate and growing. Agents should expand the scaffolding around it (indexes, digests, proposals, retrieval prompts), and you should write the notes inside it yourself. The models will keep getting better and keep getting replaced. Your own dated, linked, clearly attributed claims compound across every model you'll ever use, which is why they are worth owning.
